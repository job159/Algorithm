# A*（A-star）最短路徑：設計思路 與 走路邏輯（白話詳解）

> **一句話總結**：A* 就是「**有方向感的 Dijkstra**」。Dijkstra 只看「已經走了多少（g）」，
> 所以像水波一樣往四面八方平均擴散；A* 多加一個「**離終點大概還要多少（h）**」的樂觀估計，
> 改用 **f = g + h** 排隊 —— 永遠先處理「整條路看起來最便宜」的那一格。
> 只要 h **從不高估**，找到的仍然是最短路，但通常少看非常多格。

這份文件搭配 `a_star_pyqt6_step.py` 一起看最有感：文字講道理，動畫給你看。
建議先看過 `dijkstra/` 資料夾的 Dijkstra 教學，A* 只是在它上面加一樣東西。

## 一、先搞懂：Dijkstra 哪裡不夠好

Dijkstra 是對的、穩的，但它**完全不知道終點在哪**。

```
   Dijkstra 的探索範圍（像水波）          A* 的探索範圍（像手電筒）

        ○ ○ ○ ○ ○                              
      ○ ○ ○ ○ ○ ○ ○                            
    ○ ○ ○ ○ ○ ○ ○ ○ ○                  ○ ○ ○ ○ ○ ○ ○
    ○ ○ ○ ○ S ○ ○ ○ ○ ─ ─ ─ ► G        S ○ ○ ○ ○ ○ ○ ○ ○ ─► G
    ○ ○ ○ ○ ○ ○ ○ ○ ○                  ○ ○ ○ ○ ○ ○ ○
      ○ ○ ○ ○ ○ ○ ○                            
        ○ ○ ○ ○ ○                              
   往背對終點的方向也一樣認真找              大部分力氣花在「朝終點」的方向
```

在導航、遊戲尋路、機器人路徑規劃這種「**只要一個起點到一個終點**」的問題裡，
往反方向探索的那一半幾乎都是白做工。

> 👉 **A* 想解決的就是**：答案一樣要是最短路，但別浪費時間去看那些「明顯越走越遠」的格子。

## 二、設計思路：A* 是怎麼「想」出來的

### 第 1 步：Dijkstra 排隊看的是什麼？

Dijkstra 的優先佇列依 **g(n)** 排序：從起點走到 n「實際」花了多少。
它只回答了「**走到這裡花了多少**」，沒回答「**從這裡到終點還要多少**」。

### 第 2 步：如果我們「知道」剩下還要多少呢？

假設有個神奇函數 **h\*(n) = 從 n 到終點的真實最短成本**。
那麼 `g(n) + h*(n)` 就是「**經過 n 的最短整條路**」的成本。
永遠先處理這個值最小的格子 → 會直直沿著最短路走過去，一格都不浪費。

可惜 h\* 就是我們要求的答案，不可能事先知道。

### 第 3 步：退而求其次 —— 用「估計值」h(n) 代替

**h(n) = 從 n 到終點的「估計」成本**。最常見的估法：

> **假裝沒有牆、全是最便宜的平地**，從 n 走到終點最少要幾步？

在只能上下左右走、每格成本至少 1 的地圖上，答案就是 **曼哈頓距離 |dx| + |dy|**。

於是排隊依據變成：

```
          f(n)  =    g(n)     +     h(n)
        ───────    ─────────     ─────────────
        整條路      已經走的       離終點還要多少
        的估計      （實際，精確）  （估計，樂觀）
```

### 第 4 步：估計值有什麼條件，才不會害我們找錯？（這段最重要）

條件只有一個：**h 永遠不能高估**（術語叫 *admissible*，可採納的）：

> **h(n) ≤ h\*(n)**　── 估計值 ≤ 真實值，寧可太樂觀、不可太悲觀。

**為什麼這樣就保證最短？** 假設 A* 取出終點 G 時，`g(G) = C`，但其實存在一條更便宜的路，成本 `C* < C`。
那條更便宜的路上，一定有某一格 n 還在 Open 裡等著（還沒被處理），而且：

```
   f(n) = g(n) + h(n)
        ≤ g(n) + h*(n)        ← h 不高估
        = C*                  ← n 在那條最便宜的路上
        < C = f(G)            ← 假設
```

也就是 **f(n) < f(G)** —— 那 A* 應該會先取出 n，而不是 G。矛盾！
所以「取出 G 的那一刻」，`g(G)` 就是真正的最短成本。

> ⚠️ 反過來說：**h 一旦高估**，某些好路線的 f 被灌水、排到後面去，A* 可能先拿到一條次好的路就收工了。
> 動畫裡的「加權 3×曼哈頓」就是故意高估，你會看到它少看很多格，但總成本 21 > 最短的 18。

### 第 5 步：再加一個更強的條件，讓 Closed 不用回頭

如果 h 還滿足 **一致性（consistent）**：

> **h(u) ≤ cost(u→v) + h(v)**　── 走一步，h 最多只能減少「這一步的成本」

那麼沿著任何路線 f 都不會變小（只會持平或變大），於是：
**一格第一次從 Open 被取出時，它的 g 就已經是最短的** —— 跟 Dijkstra 的「拍板」一模一樣，
放進 Closed 之後永遠不用再打開。

曼哈頓距離在「4 方向、每步成本 ≥ 1」的地圖上：走一步 h 最多少 1，而成本至少 1 → **一致**。✓

### 白話比喻：開車找路

- **Dijkstra**：在每個路口都把「所有方向」先開一小段看看，均勻往外擴。
- **A\***：每個路口都問「**已經開了幾公里 + 這裡離目的地的直線距離**」，總和最小的先開。
  直線距離一定 ≤ 真實要開的距離（不高估），所以不會被騙；但它讓你**自然偏向目的地的方向**。

## 三、走路邏輯：拆成 6 個動作

記住五個詞：**g、h、f、Open、Closed**（再加 Dijkstra 就有的 **parent**）。

### 動作 0：準備（reset）
- `g[起點] = 0`，其它格子 `g = ∞`（還沒走到）。
- 算 `h[起點]`，`f = 0 + h`，把起點丟進 **Open**（min-heap，依 f 排序）。
- **Closed** 清空、**parent** 來源簿清空。

### 動作 1：取出 f 最小（pop）
從 Open 拿出 **f 最小**的格子 `u`。
> 平手時挑 **h 較小**的（離終點較近）→ 少繞路的小技巧，見 [Q3](#q3平手時為什麼挑-h-比較小的)。

### 動作 2：放進 Closed
`u` 處理完就不再回頭（h 一致時保證 `g[u]` 已最短）。
> 如果 `u` 就是終點 G → **結束**，答案是 `g[G]`。注意是「**取出**」G 才結束，不是「看到」G，見 [Q2](#q2為什麼取出g-才結束看到g-就停不行嗎)。

### 動作 3：更新鄰居 ★（跟 Dijkstra 的鬆弛一樣）
看 `u` 的每個鄰居 `v`（牆、已在 Closed 的跳過）：

```
   新 g = g[u] + 進入 v 的成本
   ├ 新 g < g[v]  → 更新 g[v]，算 f = 新 g + h(v)，放進 Open（動作 4）
   └ 新 g ≥ g[v]  → 不動（v 早就有一樣好或更好的走法）
```

### 動作 4：記來源（parent）
每次更新成功就記 `parent[v] = u`：「目前到 v 最便宜的走法，最後一步是從 u 過來的。」

### 動作 5：回推（backtrack）
取出 G 之後，從 G 沿著 `parent` 一路退回 S，倒過來就是路徑。

```
   G ◄─ parent ─ C ◄─ parent ─ B ◄─ parent ─ A ◄─ parent ─ S
   倒過來：S → A → B → C → G
```

> 💡 **跟 Dijkstra 的差別只有動作 1**：比的是 `f = g + h` 而不是 `g`。其它全部一樣。
> 所以把 h 設成 0，A* 就**完全等於** Dijkstra（動畫裡可以切換驗證）。

## 四、h 怎麼選：啟發函數大全

| 地圖怎麼走 | 推薦 h | 公式（dx=\|x₁−x₂\|, dy=\|y₁−y₂\|） | 不高估？ |
|---|---|---|---|
| 4 方向（上下左右） | **曼哈頓** | `dx + dy` | ✓ 最準 |
| 8 方向，斜走成本 √2 | **Octile** | `max(dx,dy) + (√2−1)·min(dx,dy)` | ✓ |
| 8 方向，斜走成本 1 | **Chebyshev** | `max(dx, dy)` | ✓ |
| 任意方向（連續空間） | **歐幾里得** | `√(dx² + dy²)` | ✓ |
| 不知道怎麼估 | **0** | `0` | ✓ 但 = Dijkstra |
| 想要快、可接受次佳 | **加權** | `w × (上面任一個)`，w > 1 | ✗ 成本 ≤ w × 最短 |

**選 h 的兩個原則：**

1. **不高估**（保證最短）。
2. **在不高估的前提下，越接近真實值越好**（看的格子越少）。

```
   h = 0          ≤      歐幾里得       ≤      曼哈頓      ≤    真實 h*    <   加權 3×曼哈頓
   (Dijkstra)            (保守)                (剛好)           (神)          (高估！)
   ◄────── 看越多格、越慢 ──────────────────────────────── 看越少格、越快 ──────►
   ◄──────────────── 保證最短 ──────────────────────────►│◄── 不保證最短 ──►
```

> ⚠️ **單位要對**：h 的單位要跟成本一樣。如果地圖上最便宜的地形成本是 0.5（不是 1），
> 曼哈頓距離就要乘 0.5，否則會高估。通式：**h = 最便宜的每步成本 × 步數下界**。

## 五、跟著手算走一遍（小例子）

6×3 的地圖，`#` 是牆，每格成本都是 1，用曼哈頓距離。S=(0,1)、G=(5,1)。

```
          x=0   1   2   3   4   5
   y=0     .    .   .   #   .   .
   y=1     S    .   .   #   .   G
   y=2     .    .   .   .   .   .
```

逐步追蹤（f 相同時挑 h 小，再一樣就照先來後到）：

| 步驟 | 取出 (g + h = f) | 新放進 / 更新 Open 的鄰居 | Open 裡 f 最小的 |
|---|---|---|---|
| 0 | — | S：g=0, h=5+0=5 → f=5 | S(5) |
| 1 | **S**(0,1)：0+5=**5** | (1,1) 1+4=5、(0,2) 1+6=7、(0,0) 1+6=7 | (1,1)=5 |
| 2 | **(1,1)**：1+4=**5** | (2,1) 2+3=5、(1,2) 2+5=7、(1,0) 2+5=7 | (2,1)=5 |
| 3 | **(2,1)**：2+3=**5** | 右邊 (3,1) 是牆！只能加 (2,2) 3+4=7、(2,0) 3+4=7 | 全部都是 7 |
| 4 | **(2,2)**：3+4=**7** | (3,2) 4+3=7 | (3,2)=7, h=3 最小 |
| 5 | **(3,2)**：4+3=**7** | (4,2) 5+2=7 | (4,2)=7, h=2 |
| 6 | **(4,2)**：5+2=**7** | (5,2) 6+1=7、(4,1) 6+1=7 | (5,2)=7, h=1 |
| 7 | **(5,2)**：6+1=**7** | G(5,1) 7+0=7 | G=7, h=0 |
| 8 | **G**(5,1)：7+0=**7** | 是終點 → 結束 | — |

**重點觀察：**
- 第 1～3 步，f 一直是 **5** —— A* 直直往 G 衝（每走一步 g+1、h−1，f 不變）。
- 第 3 步撞牆，最小的 f 從 **5 跳到 7**：「h 假裝沒有牆」的樂觀被戳破了，多出來的 2 就是繞牆的代價。
- 第 4 步有 6 格同樣 f=7，**挑 h 最小的**，於是 A* 馬上沿著牆下緣往 G 前進，不去管左邊那些 h=5、6 的格子。
- **A\* 只取出 8 格**；同一張圖用 Dijkstra（h=0）要取出 **14 格**（16 個可走格子幾乎全看完）。

**回推**：`G(5,1) ← (5,2) ← (4,2) ← (3,2) ← (2,2) ← (2,1) ← (1,1) ← S(0,1)`，總成本 **7**。

## 六、六個最容易卡住的疑問

### Q1：h 高估會怎樣？為什麼不行？
高估 = 把某些格子的 f 灌水。如果最短路上的格子被灌水，它會排在後面；
這時 A* 可能先從另一條「看起來比較便宜」的路摸到 G，**一取出 G 就收工了** → 拿到次佳解。
動畫裡選「加權 3×曼哈頓」：它直接踩過泥沼牆（成本 6）衝向 G，總成本 **21**，真正最短是 **18**。
（工程上有時故意這麼做，見 [第九節](#九工程實務真的要用時的眉角)。）

### Q2：為什麼「取出」G 才結束？「看到」G 就停不行嗎？
**不行。** 「看到」G 只代表找到**一條**到 G 的路，那時 `g[G]` 可能還會被更便宜的路更新
（例如先從泥沼那邊看到 G、後來才從平地繞過去看到更便宜的走法）。
只有 G 被**取出**時，才保證 Open 裡沒有任何一格能做出更便宜的路（第二節的證明）。
> 這是實作 A* 最常見的 bug 之一。

### Q3：平手時為什麼挑 h 比較小的？
f 相同代表「估計的整條路一樣長」。h 小 = 已經走得比較深、離 G 比較近；
先處理它，常常一路衝到 G 就結束了，不用把其他同樣 f 的格子都看一遍。
在空曠的格子地圖上，這個小技巧能讓探索範圍從「一大片」變成「一條線」。
（等價的寫法：平手時挑 g 比較大的。）

### Q4：Closed 的格子真的不用再打開嗎？
**h 一致（consistent）時不用**：一格第一次被取出時 g 已經最短（第二節第 5 步）。
如果 h 只是 admissible 但不一致，理論上可能之後找到更短的 g，正統做法要把它「重新打開」放回 Open。
本程式的曼哈頓、歐幾里得都一致；加權版本不一致，我們選擇**不重開**（工程上常見，換來速度，代價是次佳）。

### Q5：A* 一定比 Dijkstra 快嗎？
**通常快很多，但不保證。**
- 最壞情況（例如終點被一大圈牆圍住、要繞到很遠），A* 也得把大部分地圖看完，再加上計算 h 的成本。
- 預設地圖的「口袋牆」就是個小陷阱：A* 被 h 吸進口袋、撞牆、再退出來。
- Dijkstra 一次可以算出「起點到**所有**格子」的最短路；A* 只針對**一個**終點。要很多終點時 Dijkstra 反而划算。

### Q6：h 是不是越大越好？
**在不超過真實值 h\* 的範圍內，越大越好**（越準，看越少格）。
h = h\* 時 A* 只會沿著最短路走，一格都不浪費；一旦超過 h\*，就失去最短保證。

## 七、對照我們的動畫畫面

| 動畫上的東西 | 對應的概念 |
|---|---|
| 每格中央的**大數字** | `f = g + h`：經過這格的整條路估計多少（排隊的依據） |
| 格子左下 **g**、右下 **h** | 已走的實際成本 / 離終點的估計 |
| 還沒看到的格子裡淡淡的 **h=…** | h 是「每格都能事先算好」的估計值（可用核取方塊關掉） |
| 格子右上角**小徽章** | 進入這格的成本（地形權重） |
| **紫色虛線 + 標籤** | 正在處理的格子「想像」的路：無視牆、全是平地 → 就是 h |
| 下方一排**方塊（Open List）** | min-heap；最左橘色 = 下一個要取出的（f 最小，平手比 h） |
| 橘色外框那格 | 這一步正在處理的 `u` |
| 淺黃色格子 | Open：已看到、等著處理的候選 |
| 淺藍色格子 | Closed：已處理、定案 |
| **藍色細箭頭** | `parent` 來源：「我是從哪格來的」 |
| **金線從 G 往 S 長** | 回推：沿來源箭頭把路撿回來 |
| **綠色對照列** | 同一張地圖 Dijkstra 要展開幾格 vs 現在展開幾格；總成本是否最短 |

**預設地圖的三個看點**（同一張地圖、切換上方的 h）：

| h | 展開格數 | 總成本 | 看點 |
|---|---|---|---|
| h = 0（Dijkstra） | 102 | 18 ✓ | 像水波，連背對終點的左邊都看光 |
| 歐幾里得 | 75 | 18 ✓ | 有方向感，但估得比較保守（偏小）→ 看比較多 |
| **曼哈頓** | **46** | **18 ✓** | 4 方向地圖上最準的不高估估計 → 只看不到一半 |
| 加權 3×曼哈頓 | 35 | 21 ✗ | 看最少，但直接踩過泥沼牆，不是最短 |

**建議看法**：先用曼哈頓按「單步」，盯著三件事——
① 前幾步 f 是不是都一樣（直直衝向 G）？
② 衝進口袋撞牆時，Open 最小的 f 怎麼「跳」上去？
③ 找到 G 後看綠色列：比 Dijkstra 少看了多少？
然後切到「h = 0」再播一次，看探索範圍差多少。

## 八、虛擬碼 + 複雜度

```python
def a_star(graph, S, G, h):
    g = {S: 0}                        # 其它預設視為 ∞
    parent = {}
    closed = set()
    open_heap = [(h(S), h(S), S)]     # (f, h, 格子)：先比 f，平手比 h

    while open_heap:
        f, _, u = pop_min(open_heap)  # 動作1：取出 f 最小
        if u in closed:               # 過期項目（同一格被推進堆好幾次），跳過
            continue
        closed.add(u)                 # 動作2：放進 Closed
        if u == G:                    # 「取出」G 才結束（不是看到就結束）
            break

        for v in neighbors(u):        # 動作3：更新鄰居
            if v in closed:
                continue
            ng = g[u] + cost_to_enter(v)
            if ng < g.get(v, INF):
                g[v] = ng
                parent[v] = u         # 動作4：記來源
                push(open_heap, (ng + h(v), h(v), v))

    # 動作5：回推
    if G not in g:
        return INF, []                # 沒有通路
    path, cur = [G], G
    while cur != S:
        cur = parent[cur]
        path.append(cur)
    path.reverse()
    return g[G], path
```

**複雜度**（V = 格子數，E = 邊數）：
- **最壞情況跟 Dijkstra 一樣**：`O((V + E) · log V)`（h 沒幫上忙時）。
- **實際表現取決於 h 的品質**：h 越接近真實值，展開的格子越少；h = h\* 時只展開路徑上的格子。
- 記憶體：Open + Closed 可能要存很多格，大地圖時常是瓶頸（見下節）。

## 九、工程實務：真的要用時的眉角

| 眉角 | 說明 |
|---|---|
| **取出 G 才結束** | 看到 G 就停 → 不保證最短（Q2）。最常見的 bug。 |
| **破平手** | heap 的 key 用 `(f, h)` 或 `(f, -g)`；空曠地圖差非常多。 |
| **Closed / g 用陣列** | 格子地圖用 2D 陣列（或 bitset）存 g、closed，比 dict / set 快很多。 |
| **惰性刪除** | 更新 g 時直接再 push 一筆，取出時發現已在 Closed 就跳過（本程式的「過期項目」）。 |
| **h 的單位** | h = 最便宜的每步成本 × 步數下界；地形最便宜不是 1 時要記得乘上去。 |
| **8 方向不要切角** | 斜走時兩側都是牆要禁止，否則會「穿牆角」。h 用 Octile。 |
| **加權 A\*（Weighted A\*）** | `f = g + w·h`，保證成本 ≤ w × 最短。即時系統（遊戲、機器人）常用 w = 1.2～2 換速度。 |
| **大地圖** | JPS（Jump Point Search，均勻格子超快）、HPA\*（分層）、雙向 A\*、ALT（地標預算下界）。 |
| **地圖會變** | 障礙物動態出現時用 D\* Lite / LPA\*，只修補受影響的部分，不用整個重算。 |
| **車輛運動學** | 汽車不能原地轉彎 → Hybrid A\*（狀態含角度）＋路徑平滑。 |

### 最後再濃縮成三句話
1. **設計思路**：Dijkstra 只看「已經走了多少（g）」；A* 再加「離終點還要多少的樂觀估計（h）」，用 `f = g + h` 排隊，就有了方向感。
2. **走路邏輯**：取出 f 最小 → 放進 Closed → 更新鄰居（更省就更新 g、記來源、放進 Open）→ 重複 → **取出** G 時回推。
3. **為什麼還是最短**：h 從不高估，所以任何更便宜的路一定有格子的 f 比 G 小、會先被取出；h = 0 就退化成 Dijkstra，h 高估就換速度、丟保證。
